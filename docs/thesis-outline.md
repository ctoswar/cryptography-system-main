## 4. Draft: findings narrative for the Results chapter

### 4.1 The collapse of classical layering (RQ1)

The v1 design applied five keyed transformations in sequence: a Caesar shift
over the 96 printable ASCII codes (32–127), then four further repeating-key
XOR passes. Because XOR is associative and commutative, the composition is
mathematically identical to a single repeating-key XOR under the combined
mask `K1 ⊕ K2 ⊕ K3 ⊕ K4 ⊕ K5`.

This was demonstrated empirically by reconstructing v1 faithfully from the
thesis appendix source code (`evaluation/v1_reference.py`) and attacking it
(`evaluation/break_v1.py`):

- **Configuration known** (the v1 `.env` shipped the Caesar shift, prefix and
  suffix alongside the application): a single known-plaintext/ciphertext pair
  recovered the effective 16-byte mask and decrypted **8/8** session messages
  in **0.09 ms**.
- **Configuration unknown**: using only plaintext/ciphertext pairs that v1's
  own `/encrypt` endpoint published to Firebase (thesis APPENDIX F), the
  attack brute-forced the 96 Caesar shifts, recovered the padding offset and
  the full periodic mask by consistency voting, and decrypted **8/8** messages
  in **17 ms**.
- In both attacks the recovered mask equaled `K1 ⊕ K2 ⊕ K3 ⊕ K4 ⊕ K5` exactly —
  a direct proof that five "layers" provided one layer of security.
- A second design flaw was demonstrated: boot-time key regeneration
  permanently orphaned all ciphertexts from previous sessions.

### 4.2 The hybrid redesign (RQ2)

v3 (AC3-X) preserves the five-layer identity but anchors every security claim
in a citable standard: AES-256-CTR (NIST SP 800-38A) keystreams drive both
XOR passes under HKDF-derived subkeys; integrity is HMAC-SHA256 (FIPS 198-1)
applied encrypt-then-MAC (Bellare–Namprempre); the text and stream envelope
protocols use disjoint key namespaces. The full construction — key schedule,
both envelope formats, the stream MAC transcript — is specified formally in
`SPEC.md` with byte-exact conformance vectors, and three adversarial audit
rounds (44 findings and probes total) hardened the surrounding application.

### 4.3 Performance (RQ3)

Environment: see `benchmarks.json.environment`. 30 repetitions per cell;
mean ± standard deviation.

| Payload | Encrypt (MB/s) | Decrypt (MB/s) |
|---:|---:|---:|
| 1 KB | 5.5 | 7.6 |
| 64 KB | 242.1 | 218.6 |
| 1 MB | 208.3 | 175.2 |
| 10 MB | 198.5 | 191.0 |
| 100 MB | 161.1 | 158.8 |

Latency (1 KB payload, n = 1,000): mean 0.117 ms, p50 0.111 ms, p95 0.151 ms,
p99 0.200 ms. Constant-memory streaming confirmed: peak allocations of
29.4 MB (encrypt) and 25.2 MB (decrypt) while processing a 100 MB file —
0.28× the payload, independent of size. Compared with the hardened v2
pipeline (~3.7 MB/s), the hybrid is **43× faster** at large payloads because
the keystream generator is hardware-accelerated AES rather than HKDF output.

### 4.4 Statistical profile

| Metric | AC3-X | Reference / ideal | Reading |
|---|---|---|---|
| Plaintext-bit propagation | 0.087% ± 0.057% | AES-CTR baseline: 0.049% | **matches standard stream-mode behavior** — see the honest note below |
| Key sensitivity | 50.07% ± 1.06% | ideal 50% | every master-key bit fully diffuses into the ciphertext |
| Shannon entropy | 7.9771 ± 0.0017 bits/byte | max 8.0 | ciphertext byte distribution is near-uniform |
| Chi-square (df=255) | 289.16 < 293.16 | α = 0.05 | passes uniformity |

**Honest note on bit propagation (recommended thesis wording).** The classical
"avalanche effect" (~50% ciphertext change per plaintext-bit flip) is a
*block-cipher* property arising from round-based diffusion. Stream-cipher
modes — including plain AES-CTR, the industry standard this design builds on —
intentionally propagate none: flipping plaintext bit *j* flips ciphertext
bit *j* only. This is not a weakness of AC3-X relative to its reference
primitive; the measured parity with the AES-CTR baseline (0.087% vs 0.049%,
the small excess caused by the transposition layer scattering the changed
byte) demonstrates that the hybrid behaves exactly like the standard mode it
is built from. In a stream mode, confidentiality rests on keystream
unpredictability (hence the per-message nonce rule), and tamper protection is
the authenticated-MAC layer's responsibility — which is why encrypt-then-MAC
ordering is normative in the specification.

## 5. Limitations (draft, honest)

1. The Caesar and transposition layers add **no provable strength** over plain
   AES-CTR + HMAC; they are retained for continuity with the thesis design and
   act as keyed structural whitening. Any formal analysis should treat AC3-X
   as AES-CTR + HMAC with additional keyed transforms.
2. The scheme has not been independently audited; the four audit rounds
   documented in this repository were performed by the author with automated
   tooling (bandit, pip-audit, a custom escape fuzzer) and manual review.
3. **No forward secrecy — a design decision, not an oversight.** True FS
   requires destroying past key material, which conflicts with the project's
   founding principle of permanent decryptability (the cure for v1's
   orphaning flaw). v4's session mode (`AC3E.`) delivers **key separation**
   (compromise requires both the master key and the static X25519 private
   key) and public-key encryption, but not strict FS; a symmetric-ratchet
   mode (strict FS at the cost of permanent decryptability) is the documented
   future-work trade-off.
4. Nonce reuse in classic mode is catastrophic (CTR); the SIV mode exists
   precisely for deployments that cannot guarantee nonce uniqueness.
5. Statistical tests (entropy, chi-square) detect gross non-randomness only;
   passing them does not prove cryptographic security.
6. Benchmarks reflect a single machine and CPython; absolute numbers vary by
   environment (the recorded environment is captured in the results JSON).
7. CPython cannot guarantee zeroization of discarded secrets (ephemeral
   session keys).

## 6. Suggested contributions statement

1. An empirical demonstration that classical multi-layer XOR/Caesar composition
   collapses to a single XOR, with a working known-plaintext attack against a
   faithful reconstruction of the original design.
2. A re-engineering methodology that preserves a legacy design's identity
   while relocating every security claim onto standard, citable primitives.
3. A formal specification with conformance vectors enabling independent
   implementation and byte-exact verification.
4. A reproducible evaluation suite (one command regenerates all results and
   figures) covering performance, latency, memory behavior, and statistical
   ciphertext properties.
5. A documented three-round adversarial audit methodology with all findings,
   fixes, and regression tests published in the repository history.
6. **A fourth, design-level audit round (v4)**: after the implementation was
   hardened, the design's own documented weaknesses were systematically
   remediated — versioned key rotation (never orphaning history), an
   RFC 5297 misuse-resistant mode for nonces, and an RFC 7748 X25519 session
   mode delivering key separation and public-key encryption — together with
   an explicit analysis of why strict forward secrecy conflicts with the
   design's permanent-decryptability principle, and what a ratchet mode
   would cost.
